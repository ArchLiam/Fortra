## 2. Cross-Cutting Architecture Notes

These themes recur across the design docs; read them once before diving into individual entries.

**Pricing pre-/post-hook waterfall.** Fortra layers several Apex pricing pre-hooks (and one
post-hook) onto the Revenue Cloud pricing procedure via the Procedure Plan Definition. As stated
across the docs, the custom-step order is roughly:

1. **Hardware Attribute Pricing** — after List Price, before Regional/Partner (Power products).
2. **Regional Services Pricing** (`RegionalServicesPricingPrehook`) — first generic custom step; a
   matching **post-hook** re-asserts the regional price onto `NetUnitPrice` as last writer.
3. **Partner Pricing** (`PartnerPricingPrehook`) — after Regional, before COLA.
4. **Attribute Volume Pricing** (`AttributeVolumePricingPrehook`) — §3 of `Fortra_Pricing_PreHook`,
   after Regional/Partner, before the price procedure.
5. **COLA Uplift** (`COLAUpliftPrehook` / `COLAUpliftHandler`) — renewal quotes only.

> ⚠️ **Ordering caveat to verify in-org:** the COLA doc states COLA is applied *before* Regional and
> that the two **compound** (`Final = (Asset.Price × (1 + COLA%)) × Regional Multiplier`), whereas the
> Partner/Attribute docs place COLA *after* Regional. These operate on different bases (COLA off the
> renewing **Asset** price; Regional off **list** price) and in different contexts (renewal vs new),
> which likely explains the apparent conflict — but confirm the live Procedure Plan order before
> relying on either. Every pre-hook is **fail-safe**: it returns `SUCCESS` on error and uses a static
> recursion-guard flag, so a pricing bug degrades gracefully rather than blocking the save.

**Declarative-first, Apex-where-required.** Several modules are deliberately *no-Apex* (ARR,
Amendments, Create New Quote, Opportunity Legal Entity Change, MultiCurrency) — built from flows,
formulas, validation rules, Dynamic Forms, and Context Definition mappings. Apex appears where the
platform can't express the logic declaratively (pricing pre-hooks, bulk repricing controllers,
exchange-rate lookups, checklist services, asset-contract linking).

**Context Definition hydration is load-bearing.** Any custom field that must flow Quote→Order (or
QLI→OrderItem) needs an explicit **hydration mapping** in the Sales Transaction Context Definition
(`SalesTransactionContextExt` / `FortraSalesTransactionContext`). Pricing pre-hooks can only write
context attributes that are hydration-mapped; an unmapped attribute fails silently. This is the
single most common source of "the value didn't carry over" bugs.

**Q2O → Asset → Billing → Renewal/Amendment lifecycle.** The canonical transaction spine is
Quote → Order (`createOrderFromQuote`) → Asset (`createOrUpdateAssetFromOrder`) → Billing Schedule,
then Renewal (a *new* Contract generation linked by `Original_Contract__c`) or Amendment (a *child*
Contract via `AmendedContractId`). Assetization requires an **ApplicationUsageAssignment** (AUA) with
`AppUsageType = RevenueLifecycleManagement` — a missing AUA is the #1 cause of "no Asset created."
Assetization and Billing fire as **independent parallel async triggers** on `Order.Status = Activated`.

**Multi-currency invariant.** Order, OrderItem, and Contract must share the same `CurrencyIsoCode`
or DML throws `FIELD_INTEGRITY_EXCEPTION`. Currency is driven top-down from the Account's default
Legal Entity; Salesforce blocks changing an Opportunity's currency once Quotes exist (worked around
by the Legal-Entity-Change quick action and the denormalized `Quote_Count__c` counter).

**Role-based amendment guardrails.** Sales users (roles *not* containing "Customer Ops"/"Operations")
are blocked by validation rules from creating Downsell/Full-Cancellation amendments, and from any
non-Upsell/Cross-sell amendment inside the **120-day renewal window** — a constant that is currently
hardcoded in formulas/VRs across the Amendments and Contracts docs.

**Metadata-API gaps require manual config.** Permission-set FLS for some sets, Path Assistant,
Dynamic Forms, certain picklist values, and LWC placement on Lightning pages cannot be fully deployed
via Metadata API and are called out as manual post-deploy steps in multiple docs.

## 3. Pricing

### Pricing ARR (`Fortra-Pricing-ARR-Solution-Design-Doc.docx`)
- **Purpose / Scope:** Provides automatic Annual Recurring Revenue calculation and tracking across the quote-to-cash lifecycle (Quote → Order → Asset), normalizing multiple billing frequencies to an annualized figure, with displaced-ARR tracking and renewal approval workflows. Implemented entirely declaratively (flows, formulas, roll-ups), no Apex.
- **Key Design Decisions:** Before-save flow calculates ARR on QuoteLineItem; values propagate via Context Definition mapping (Q2O) and an asset-triggered flow (System Mode Without Sharing) traversing the AssetAction/AssetActionSource chain. Three-tier displaced-ARR logic (Replaced Asset → manual input via Swap). Approval gating via checkbox flags. `Quote_Line_ARR__c` converted from formula to currency field to enable flow writes and roll-ups.
- **Objects / Fields / Components:** Flows: `Fortra_QuoteLineItem_Calculate_ARR` (before-save), `Fortra_Quote_Line_Item_Calculate_Total_ARR` (after-save), `Fortra_Asset_Copy_ARR_From_OrderItem`, `Fortra_Opportunity_Line_Item_Calculate_Total_ARR`, plus two approval-criteria screen flows (`Fortra_Quote_Displaced_ARR_Approval_Criteria`, `Fortra_Quote_Discount_Renewal_ARR_Approval_Criteria`). Fields: `QuoteLineItem.Quote_Line_ARR__c`, `Displaced_ARR__c`, `Replaced_Asset__c`; `Quote.Total_ARR__c`, `Total_Displaced_ARR__c`, `Amendment_ARR_Impact__c`, `Original_Contract_ARR__c`; `OrderItem.Order_Line_ARR__c`; `Asset.ARR__c`; `Contract.Contract_ARR__c`; `Product2.Primary_Catalog_Name__c`/`Primary_Category_Name__c`/`Parent_Category_Name__c`/`Product_Selling_Model_Type__c`. Custom Report Type "Fortra ARR Report Type."
- **Business Rules / Logic:** Annualization: Annual = TotalLineAmount/PricingTermCount; Semi-Annual ×2; Quarterly ×4; Monthly ×12. Null/zero PricingTermCount, null TotalLineAmount, or OneTime/missing selling model → ARR 0. Displaced ARR: Replaced_Asset.ARR__c first, else Displaced_ARR_Input__c if Swap__c true, else 0. Asset copy only when source differs and is non-null. Example: $36,000 / 3-yr = $12,000 ARR.
- **Integration / Dependencies:** Revenue Cloud Context Definition (Q2O), assetization chain (`createOrUpdateAssetFromOrder`, `Fortra_Assetize_Order`), `Fortra_Quote_to_Order_Conversion`, standard ProductSellingModel. Product Mgmt maintains hierarchy fields; Sales Ops defines approval thresholds.
- **Open Items / Risks / Notes:** Assumes Context Definition mappings exist in both DP2 and UAT. Product hierarchy fields manually maintained (risk of staleness). Approval thresholds for Displaced/Renewal ARR TBD by Sales Operations.

### Pricing Attribute Volume Pricing (`Fortra-Pricing-AttributeVolumePricing-Solution-Design-Doc.docx`)
- **Purpose / Scope:** Dynamic pricing engine that sets product price from a six-dimensional match (Product, ProductSellingModel, Attribute Name, Attribute Value, Quantity Lower/Upper Bound), letting admins add pricing rules as data without code changes.
- **Key Design Decisions:** Apex pre-hook `AttributeVolumePricingPrehook` running as Section 3 of `Fortra_Pricing_PreHook` (after Regional §1 and Partner §2, before Price Procedure §4). Governor-safe two-pass bulk pattern: Pass 1 collects Product/PSM IDs → single SOQL → composite-key map (`ProductId|PSMId|AttrName|AttrValue`); Pass 2 dynamically iterates every attribute with in-memory quantity-range validation (exactly one SOQL regardless of line count). Recursion prevention via static `isUpdating` flag.
- **Objects / Fields / Components:** Apex `AttributeVolumePricingPrehook` (+ test). Custom object `Attribute_Tier_Pricing_Storage__c` (`Product__c`, `Product_Selling_Model__c`, `Attribute_Name__c`, `Attribute_Value__c`, `Lower_Bound__c`, `Upper_Bound__c`, `Tier_Value__c`, `Price_Mode__c`, `Multiplier__c`). Context OUTPUT attrs on SalesTransactionItem: `Base_Price__c`, `Attribute_Price_Mode__c`, `AttributeMultiplierPct__c`, `AttributePricingApplied__c`, `AttributePricingExplainer__c`, `Attribute_Feature__c`, `Attribute_Quantity__c`. Eligibility flag `QuoteLineItem.Has_Attribute_Adjustment__c`. Three pricing-procedure List Operation elements.
- **Business Rules / Logic:** Only `Has_Attribute_Adjustment__c = true` lines processed. Both bounds inclusive. Three modes: Unit Price (`Base_Price__c` → InputUnitPrice); Calculated (`Base_Price__c × AttributeMultiplierPct__c` → ItemNetTotalPrice); Total Price (`Base_Price__c` → ItemNetTotalPrice). No match → line skipped, standard pricing falls through. Delete-context non-updatable errors caught, returns SUCCESS.
- **Integration / Dependencies:** Procedure Plan Definition; Context Definition (reads SalesTransactionItem + SalesTransactionItemAttribute, writes 7 outputs via `updateContextAttributes`, only hydration-mapped attrs to avoid silent batch failure). Depends on Regional/Partner prehooks deployed.
- **Open Items / Risks / Notes:** Assumes non-overlapping quantity ranges per Product/PSM/Attribute combo. `RevSignaling.TransactionRequest` cannot be mocked — relies on `@TestVisible` + integration testing. Goals: -50% pricing tickets, -30% quote time.

### Pricing COLA (`Fortra-Pricing-COLA-Solution-Design-Doc.docx`)
- **Purpose / Scope:** Automatic annual Cost-of-Living-Adjustment uplift on subscription renewal quotes, using the current Asset price as base and a Solution-Category rate. Covers 20 categories, rates 0% (Fortra Platform) to 9.85% (Robotic Process Automation).
- **Key Design Decisions:** Dual automation: trigger handler `COLAUpliftHandler` (before-insert/update) populates fields and recalculates price; `COLAUpliftPrehook` writes context attrs for waterfall visibility. Three-tier override hierarchy: Line Override > Contract Override > CMDT Lookup, tracked by `COLA_Source__c`. `AssetContractQueryHelper` (without sharing) for restricted AssetContractRelationship/Contract access. Rates in `COLA_Uplift_Rules__mdt`.
- **Objects / Fields / Components:** Apex: `COLAUpliftHandler`, `COLAUpliftPrehook`, `AssetContractQueryHelper` (+ test). CMDT `COLA_Uplift_Rules__mdt` (`Solution_Category__c`, `Default_Uplift_Percent__c`, `Is_Active__c`, `Effective_Start/End_Date__c`, `Description__c`). 10 QuoteLineItem fields (`COLA_Uplift_Percent__c`, `Default_COLA_Uplift_Percent__c`, `Pre_COLA_Price__c`, `COLA_Solution_Category__c`, `COLA_Applied_Date__c`, `COLA_Modified_By/Date__c`, `COLA_Override_Reason__c`, `Is_COLA_Overridden__c` formula, `COLA_Source__c`). Contract: `COLA_Override_Percent__c`, `COLA_Override_Persist_Until__c`. `COLA_Admin` permission set; `COLAUpliftPass`/`COLAUpliftFail` ExplainabilityMsgTemplates. Context outputs: `COLACalculatedPrice__c`, `COLAUpliftPercent__c`, `COLAExplainer__c`, `COLAApplied__c`.
- **Business Rules / Logic:** UnitPrice = `Pre_COLA_Price__c × (1 + COLA%/100)` (e.g., $10,000 × 1.0785 = $10,785). Only `QuoteAction.Type='Renew'`. Solution Category from `Product2.Solution_Category__c`; none → 0%. Contract override valid when Status='Activated', percent not null, and persist-until null (one-time) or ≥ today (multi-renewal); past = expired. Line edit recalculates off preserved base, sets source 'Line Override'. SUCCESS on error.
- **Integration / Dependencies:** Asset.Price via `QuoteAction.SourceAssetId`; AssetContractRelationship; ProductCategory hierarchy; pricing procedure pre-hook section. Owners: Finance (rates), Contract Mgmt (overrides), IT Admin (CMDT).
- **Open Items / Risks / Notes:** New Solution Categories need new CMDT records. **COLA applied BEFORE Regional Pricing; the two compound:** Final = (Asset.Price × (1+COLA%/100)) × Regional Multiplier. *(See the ordering caveat in §2.)*

### Pricing Partner Pricing (`Fortra-Pricing-PartnerPricing-Solution-Design-Doc.docx`)
- **Purpose / Scope:** Applies partner-specific (reseller/distributor/referral) pricing adjustments during quoting, automating partner-adjusted prices for two models: Guaranteed Margin (additive multi-partner) and Discount (single billing partner).
- **Key Design Decisions:** Apex pre-hook `PartnerPricingPrehook` positioned after Regional Services Pricing, before COLA Uplift (waterfall Step 4). Layered architecture (data object / `PartnerPricingService` logic / prehook integration). Context API only (no direct DML). Additive (not multiplicative) margin stacking. Dual-field writes (standard `PartnerUnitPrice`/`PartnerDiscountPercent` + custom audit) for TLE display. Fail-safe SUCCESS + static recursion flag.
- **Objects / Fields / Components:** Apex `PartnerPricingPrehook.cls`, `PartnerPricingService.cls`. Custom object `Partner_Pricing_Model__c` (Master-Detail Account; `Model_Type__c`, `Is_Active__c`, `Is_Default__c`, five percents: `Software_Percent__c`/`New_Maintenance_Percent__c`/`Renewal_Maintenance_Percent__c`/`Subscription_Percent__c`/`Services_Percent__c`, `Effective_Start/End_Date__c`). Quote fields: `Billing_Partner__c`, `Partner_Pricing_Model__c`, `Reseller__c`, `Distributor__c`, `Referral_Partner__c`. 8 QuoteLineItem fields incl. `Pre_Partner_Price__c`, `Partner_Adjusted_Price__c`, `Partner_Discount_Percent__c`, `Partner_Margin_Detail__c` (JSON), `Partner_Pricing_Warning__c`. Permission sets `Partner_Pricing_Admin`/`_User`. 18 context attrs in `SalesTransactionContextExt`.
- **Business Rules / Logic:** Discount: List × (1 − Billing Partner Discount%), e.g., $1,000 × 0.80 = $800. Guaranteed Margin (additive): List × (1 − SUM all margins%), e.g., 15%+10%=25% → $1,000 × 0.75 = $750. Product-type → field mapping (Software/Perpetual, New/Renewal Maintenance, Subscription/SaaS, Services/Prof Svc). Only Is_Active + in-date models. Price source: context UnitPrice first, fall back to ListPrice. Clears all 9 output fields when partner pricing no longer applies; writes warning when partner lacks model.
- **Integration / Dependencies:** Context API (`queryTags`/`updateContextAttributes`); Procedure Plan after RegionalServicesPricingPrehook; needs `Fortra_Product_Type__c` populated; 18 attrs `fieldType=inputoutput, transient=false`. Requires Revenue Cloud / BRE licenses.
- **Open Items / Risks / Notes:** Only one active model per type per partner. `Billing_Partner__c` drives the Discount model; other partners participate only in Guaranteed Margin. 85%+ test coverage required.

### Pricing Regional Pricing (`Fortra-Pricing-RegionalPricing-Solution-Design-Doc.docx`)
- **Purpose / Scope:** Country-based pricing multipliers for Services products sold globally — 177 countries across 5 regions (APAC, EU, LATAM, MEA, NA), multipliers 0.30 (Argentina) to 1.015 (UK), adjusting list price by the Quote's shipping country.
- **Key Design Decisions:** Dual-hook architecture: `RegionalServicesPricingPrehook` sets regional-adjusted UnitPrice before the procedure; `RegionalServicesPricingPosthook` writes the regional price to NetUnitPrice as last-writer after the procedure. CMDT storage (zero-SOQL) plus a Decision Table for declarative lookups. Product opt-in via checkbox. First custom step in the waterfall. Post-hook dynamically chains to PartnerPricingPosthook via `Type.forName()`.
- **Objects / Fields / Components:** Apex pre/post hooks. CMDT `Services_Regional_Pricing__mdt` (`Country__c`, `Country_Code__c`, `Region__c`, `Subregion__c`, `Multiplier__c` Number(4,2), `Is_Active__c`, `Effective_Start/End_Date__c`). Custom object `Regional_Pricing_Entry__c` (Decision Table source). Decision Table `DT_Fortra_Regional_Pricing`. `Product2.Allow_Regional_Pricing__c` (default false). QuoteLineItem audit fields: `PrehookRSNetUnitPrice__c`, `RegionalPricingExplainerItem__c`, `RegionalNetUnitPrice__c`, `Pre_Regional_Price__c`, `Regional_Multiplier__c`.
- **Business Rules / Logic:** Adjusted Price = CEILING((ListPrice × Multiplier)/5) × 5 (round UP to nearest $5). Example: $1,247 × 0.65 = $810.55 → $815. Country lookup: `ShipToPlace_Country__c` then `ShippingCountry` fallback (name and code indexed). Unlisted countries → 1.0 (no adjustment, skip update). Only `Allow_Regional_Pricing__c=true` products. Post-hook reads `RegionalNetUnitPrice__c` → NetUnitPrice so it survives PriceRevision overwrites. Fail-safe SUCCESS.
- **Integration / Dependencies:** Context API; both hooks registered in Procedure Plan; CMDT cached; Decision Table from `Regional_Pricing_Entry__c`. Requires Revenue Cloud license with Decision Table access.
- **Open Items / Risks / Notes:** Multipliers denominated in USD, applied before currency conversion. CSV accuracy of 177 multipliers assumed verified by Fortra stakeholders. Effective-dating is Low priority.

### Maintenance (Derived) Pricing (`Fortra-Maintenance-Derived-Pricing-Solution-Design.docx`)
- **Purpose / Scope:** Prices auto-added maintenance/support lines as the related license's list price × a tier-dependent percentage. Fixes lines that price at $0 across ~1/3 of the catalog (selling-model mismatch) and a multiplicative price-shrinkage defect on repricing. (Consultant: Coastal; v1.0, June 6 2026.)
- **Key Design Decisions:** No custom Apex prehook — a prehook was empirically abandoned because for `IsDerived` lines the native derived-pricing element owns Net Unit Price and discards prehook writes. Instead, stamp the source license list price onto the maintenance line as data, then a Formula Based Pricing element multiplies that stamped value. This sidesteps the native contributor-resolution step (which only works when license and maintenance products share a selling model) and avoids shrinkage by multiplying a stable stamped field rather than NetUnitPrice itself.
- **Objects / Fields / Components:** New field `QuoteLineItem.Source_List_Price__c` (Currency; must be hydration-mapped into `_v2` sales-transaction context). Record-Triggered Flow "Stamp Source List Price." Pricing-procedure "Derived Pricing Formula" (Formula Based Pricing, List Container 9). Native "Derived Pricing Data Retrieval" (Derived Price) element. Existing `MTD`/`MaintenanceType` product attribute (already on 184 maintenance products). Tier rates in `Maintenance_Rate` custom metadata. Relationship via existing `PriceBookEntryDerivedPrice.ContributingProductId`.
- **Business Rules / Logic:** Tier rates: Premier 30%, Standard 20%, Professional 20%. Flow reads source license's non-derived PricebookEntry list price (quote's price book + currency, IsDerived=false) → `Source_List_Price__c`. Formula: `IF(tier='Premier',0.30, IF('Standard',0.20, IF('Professional',0.20, <fallback>))) × Source_List_Price__c` → NetUnitPrice.
- **Integration / Dependencies:** None external — entirely within Revenue Cloud. Operational dependency: manual Decision Table refresh after pricing-data/formula changes.
- **Open Items / Risks / Notes:** **First validation step gates the build:** on mismatched product `FIM-FIM-RRM-TECRM`, confirm whether native "Derived Pricing Data Retrieval" hard-errors (then remove it) or returns $0 (then retain; formula overwrites). Tier fallback/data hygiene TBD: trailing '0' yields $0 for blank/off-list tiers; re-tag four straggler products (Premium ×2, Expert ×1, platinum ×1) to live tiers or confirm dead. Requirements/Assumptions/Dependencies tables are template placeholders (`[Requirement]`/`[Assumption]`/`[Dependency]`, all unfilled).

## 4. Quotes

### Quotes Amendments Solution Design (`Fortra-Quotes-Amendments-Solution-Design-Doc.docx`)
- **Purpose / Scope:** Extends the standard Quote object to support mid-term contract amendments with role-based access controls, financial-impact tracking, and pro-ration calculations, using the existing `Quote_Type__c` = 'Amendment' value rather than a separate Record Type.
- **Key Design Decisions:** Declarative, no-Apex architecture (custom fields, formulas, validation rules, Layout, FlexiPage). Reuses `Quote_Type__c` picklist + Lightning Dynamic Forms instead of a Record Type. Defense-in-depth validation: four independent rules rather than compound conditions. A formula chain (`Renewal_Contract__c` → `Original_Contract_ARR__c`/`Days_Until_Renewal__c` → `Within_Renewal_Window__c` → restriction VR) keeps calcs real-time. Co-termination handled via Contract record-triggered flows.
- **Objects / Fields / Components:** Quote: `Amendment_Reason__c` (restricted picklist, 10 values: Upsell, Cross-sell, Downsell, Full Cancellation, Withholding Tax, Billing Correction, Partner Change, Currency Change, Billing Entity Change, Other), `Amendment_Request_Date__c`, `Amendment_Effective_Date__c`, `Amendment_ARR_Impact__c` (Currency 18,2), `Pro_Ration_Method__c` (Daily/Monthly-default/Full Period/No Pro-ration), `Pro_Rated_Amount__c`, `Credit_Amount__c`; formulas `Original_Contract_ARR__c`, `Days_Until_Renewal__c`, `Within_Renewal_Window__c`, `Net_Contract_Change__c`. Contract: `Parent_Contract_End_Date__c`, `Co_Term_Overridden__c`. Layout: Amendment Quote Layout; FlexiPage: `Quote_Record_Page_With_Amendments`. VRs: `Require_Amendment_Reason`, `Amendment_Requires_Contract`, `Sales_Cannot_Create_Downsell`, `Enforce_Amendment_Sales_Restriction`, `Enforce_Discount_Cap`.
- **Business Rules / Logic:** `Original_Contract_ARR__c` = `Renewal_Contract__r.Expected_Ren_Amount__c`; `Days_Until_Renewal__c` = `Renewal_Contract__r.EndDate - TODAY()`; `Within_Renewal_Window__c` = TRUE when contract linked and days 0-120 inclusive; `Net_Contract_Change__c` = `Amendment_ARR_Impact__c - Credit_Amount__c`. Sales (roles not containing 'Customer Ops'/'Operations') blocked from Downsell/Full Cancellation always, and from any non-Upsell/Cross-sell amendment within the 120-day window. `Enforce_Discount_Cap` blocks >30% discount when Status='Presented' and not Approved. Co-term flows auto-set amendment EndDate to parent EndDate and flip `Co_Term_Overridden__c` on divergence. Formulas use BlankAsZero.
- **Integration / Dependencies:** `Fortra_Opportunity_Create_New_Quote_From_Opportunity_Flow` (Amendment type + reason), standard Q2O (`Fortra_Quote_to_Order_Conversion`), Contract co-term flows (`Contract_Amendment_CoTermination`, `Contract_Amendment_CoTerm_Override_Detection`), discount approval (`DiscountApprovalStatus__c`). Requires RCA, multi-currency, Dynamic Forms; deploys via Metadata API v59.0.
- **Open Items / Risks / Notes:** 120-day window is hardcoded in formulas/VRs (assumption A-007). Assumes `Quote_Type__c`, `Renewal_Contract__c`, and `Contract.Expected_Ren_Amount__c` already exist; role names must contain 'Customer Ops'/'Operations' for bypass logic.

### Quotes Create New Quote Solution Design (`Fortra-Quotes-Create-New-Quote-Solution-Design-Doc.docx`)

### Exchange Rate Snapshot Solution Design (`Exchange Rate Snapshot Solution Design.docx`)
- **Purpose / Scope:** Captures and persists the transaction-currency→USD exchange rate at multiple levels (QLI, OrderItem, Opportunity) across the Revenue Cloud quoting/ordering pipeline so Workday and downstream integrations always have a non-null rate. Delivered in three phases.
- **Key Design Decisions:** Single reusable `DatedConversionRateLookup` Apex `@InvocableMethod` as the sole rate source (callable from triggers and Flows), using ACM `DatedConversionRate` with `CurrencyType` fallback. One-trigger-per-object: `QuoteLineItemExchangeRateTrigger` handles Phase 1 (before) + Phase 2 (after); `OpportunityTrigger` handles Phase 3 (before) + existing Hardware after-update logic. Zero-DML before-trigger field assignment for QLI and Opportunity (1–2 SOQLs only). Phase layering ensures the field is never null: Phase 3 sets initial rate at creation; Phase 2 overwrites with the QLI-priced rate (which takes precedence).
- **Objects / Fields / Components:** Apex: `DatedConversionRateLookup`, `QuoteLineItemExchangeRateTrigger`, `OpportunityTrigger`, `OpportunityTriggerHandler` (`handleBeforeInsert`, `handleBeforeUpdate`, private `setExchangeRates`). Field `Exchange_Rate_To_USD__c` (Number(18,10)) on QuoteLineItem, OrderItem, Opportunity. Standard objects `DatedConversionRate`, `CurrencyType`. Context Definition `SalesTransactionContextExt` (hydration). Permission Set `OrderItem_Field_Access`.
- **Business Rules / Logic:** Phase 1 — QLI before-trigger builds a request per `CurrencyIsoCode` (skip blanks), calls `getExchangeRates()` once, sets field in-place; USD→1.0, unknown→null. Phase 2 — after-trigger propagates QLI rate to Opportunity ONLY when the QLI's Quote = `Opportunity.SyncedQuoteId` (syncing-quote guard prevents stale rates); uses `Database.update(allOrNone=false)` so Opportunity VR failures don't block the QLI save. Phase 3 — Opportunity before-insert sets rate for all; before-update only when `CurrencyIsoCode` actually changed. Rate lookup: query `DatedConversionRate` by ISO + date range, fall back to active `CurrencyType`.
- **Integration / Dependencies:** Workday reads `Exchange_Rate_To_USD__c` from Opportunity (deal-level) and OrderItem (line-level). QLI→OrderItem propagation via `SalesTransactionContextExt` hydration (mappings under both QuoteEntitiesMapping and OrderEntitiesMapping). Independent of the RC pricing pipeline — works for manually-priced/zero-dollar lines. Requires ACM enabled; corporate currency USD.
- **Open Items / Risks / Notes:** Assumes all active currencies have `DatedConversionRate`/`CurrencyType` records (A-002). `Exchange_Rate_To_USD__c` is read-only for downstream consumption (A-004). External deps: manual Context Definition hydration config, FLS, and Workday integration config (E-001/E-002/E-003). All internal dependencies marked Complete.

### Opportunity Legal Entity Change (`Opportunity Legal Entity Change.docx`)
- **Purpose / Scope:** Provides a guided Quick Action workflow to change the Legal Entity on an Opportunity while enforcing multi-currency integrity, since Salesforce blocks direct currency changes on an Opportunity that already has Quotes when the new Legal Entity uses a different currency.
- **Key Design Decisions:** 6 components across 4 phases: screen flow, two Quote-count record-triggered flows, a `Quote_Count__c` custom field, a validation rule, and the Quick Action. Denormalized counter pattern: `Quote_Count__c` works around the fact that validation rules cannot run aggregate subqueries on child records. Dual-control: Validation Rule blocks risky inline edits; Quick Action provides the guided path. Two separate count flows because contexts differ: After Save (create, includes new record) vs Before Delete (subtract 1, record still present).
- **Objects / Fields / Components:** Screen Flow `Fortra_Opportunity_Change_Legal_Entity` (4 decisions, 3 updates, 1 delete, 6 screens). Record-triggered flows `Fortra_Quote_Count_Maintenance` (Quote After Create) and `Fortra_Quote_Count_Maintenance_Delete` (Quote Before Delete). Field `Opportunity.Quote_Count__c` (Number(18,0), default 0). Validation Rule `Legal_Entity_Requires_Action`. Quick Action `Opportunity.Change_Legal_Entity` (Flow type). Objects: Opportunity (`Legal_Entity__c` lookup→LegalEntity, `CurrencyIsoCode`), standard LegalEntity (`CurrencyIsoCode`, `Name`), Quote (`OpportunityId`). FlexiPage `Opportunity_Record_Page_Two_Column`. Related quote-creation flow `Fortra_Opportunity_Create_New_Quote_From_Opportunity_Flow`.
- **Business Rules / Logic:** Decision tree — same LE selected → No-Change screen; currency match → update `Legal_Entity__c` only; currency differs & `Quote_Count__c = 0` → update LE + `CurrencyIsoCode`; currency differs & Quotes exist → warning screen (radio: delete all & proceed / cancel) → on delete: delete all Quotes WHERE `OpportunityId = recordId`, then update LE + Currency + reset `Quote_Count__c` to 0. Validation Rule: `ISCHANGED(Legal_Entity__c) AND NOT(ISBLANK(Legal_Entity__c)) AND Quote_Count__c > 0 AND TEXT(Legal_Entity__r.CurrencyIsoCode) <> TEXT(CurrencyIsoCode)`. Delete-count flow subtracts 1 to compensate for Before Delete context. All DML has fault connectors routing to an error screen showing `$Flow.FaultMessage`.
- **Integration / Dependencies:** Leverages Salesforce Multi-Currency; standard LegalEntity object (introduced with Revenue Cloud). Quote deletion cascades to QuoteLineItems/children. Integrates with `Fortra_Opportunity_Create_New_Quote_From_Opportunity_Flow` for post-change quote recreation. TR-001 requires `flowruntime:lookup` component.
- **Open Items / Risks / Notes:** A-005 — `Quote_Count__c` may need a data fix to backfill existing Opportunities at deploy. A-006 — Quote deletion is a HARD delete; unrecoverable after recycle-bin retention expires. Users need Quote delete permissions (E-003). All internal dependencies marked Complete.
