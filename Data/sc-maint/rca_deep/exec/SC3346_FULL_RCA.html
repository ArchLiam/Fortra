1 · The defect — in business terms

When a customer renews their BoKS maintenance, the renewal line priced at the wrong amount — a stale $60.64 (a one-period double-discounted fossil, = 67.38 × 0.90) or $0 — instead of the correct cost-of-living-adjusted renewal of $67.38 (last year’s net $62.48 × 7.85% COLA). The COLA arithmetic was never wrong; the value simply never committed to the line. Several prior remediation attempts failed because every one of them tried to write the price at reprice time — the wrong layer entirely.

2 · Root cause — a selling-model mismatch (found via end-to-end debug)
  1. New-business maintenance (PIA-PIA-RNM-PIAMBK) is sold under a One-Time selling model, so the asset the customer owns is One-Time — not a renewable subscription.
  2. The platform’s initiateRenewal therefore tags that asset’s renewal as QuoteAction.Type = “No Change”, Quantity 0 — which never enters the Renew-gated COLA path (COLAUpliftonRenewalNet). Term-Based subscriptions (beSECURE) renew as Renew and price correctly.
  3. The legacy Year-2 AutoAdd rule then deletes that owned-asset line and substitutes an asset-less Renewal-Maintenance line (PIA-PIA-RRM-PIAM) with no contributor — the native DerivedProductsRenewals committer skips it, so its price freezes at the fossil or $0.
  4. The fix: stop discarding the owned line — flip it to Renew and let the native engine apply the COLA uplift to last year’s net. No new pricing logic, no catalog change, no selling-model change.
3 · The investigation — phase by phase
  • Symptom triage & scope
    Renewal-maintenance committing $60.64 / $0 vs the COLA-correct $67.38. COLA math verified correct; the value was not persisting to the line.
  • Two mechanisms separated
    A1 (partner double-discount, posthook-version dependent) vs A2 (no priced node at all) — sequential, not competing. The earlier qty-based framing was tested and set aside.
  • Contributor model established
    A derived renewal prices only from a contributor: the prior owned Asset surfaced via QuoteAction(Type=Renew).SourceAsset, matched by product. No contributor → the committer skips the line.
  • Reprice-time writes refuted (×3)
    Direct NetUnitPrice write (read-only on insert), PartnerNetPricePosthook, and a procedure committer all returned success yet no-oped on a settled derived node.
  • Self-healing candidate rejected
    The “lever-d” procedure-commit change could self-heal existing fossils, but could not be proven to fire (the $67.38 in those logs was prehook-sourced, byte-identical across runs) → rejected as unproven/unsafe.
  • Born-net & PBEDP dead-ends
    Hand-stamping a Renew QuoteAction after insert was too late (line settles at $0). Mapping the owned product as a price contributor (PBEDP) is platform-blocked — it is itself a derived product.
  • Decisive E2E debug — root cause exposed
    Running the real initiateRenewal with debug logging showed it emitting No Change / qty 0 for the One-Time maintenance asset — the line that never enters the COLA path. The fix writes itself: flip to Renew.

5 · The fix — design, code & wiring

Apex · RenewalMaintenanceFlip

Selects renewal-quote lines that are owned-maintenance carryover stuck on No Change, and flips them:

  • QuoteAction.Type → Renew
  • line StartQuantity = 0, Quantity = SourceAsset.Quantity
  • bulk-safe, idempotent, null/empty-safe
  • @InvocableMethod for clean Flow binding

DEPLOYED API 64 · 4/4 tests pass · 100% class coverage

Flow · Fortra_Create_Renewal_Quote

Wired so every renewal automatically runs flip → reprice:

initiate renewal → populate dates →
Flip Maintenance (apex) → Reprice (subflow) → $67.38 committed

Reprice = Place Sales Transaction, pricingPref:Force, configurationPref:{configurationMethod:Skip}.

7 · Honest caveats & scope

Forward-only fix

The flip corrects renewals as they are generated (the wired flow / on-demand flipToRenew). It does not retroactively heal already-settled fossil lines on pre-existing Draft quotes — those need a separate remediation reprice.

Known residuals to confirm

  • The exact platform reason a direct NetUnitPrice write no-ops is empirically strong (reproduced 3×) but not mechanistically pinned.
  • The 7.85% rate comes from a COLA-rate custom metadata rule; the exact record was not re-pinned this pass — verify before prod.
