SC-3390 ADVERSARIAL VERIFICATION — CANDIDATE [static-recursion-guard-skips-effective-pass]
Verifier run: 2026-06-11 (read-only, FortraUAT). Verdict: REFUTED (as primary mechanism) / at most inert defensive guard.

CANDIDATE CLAIM
  isUpdating static guard (cls 30,65-67,72,78) early-returns 'Skipping recursive execution' WITHOUT pricing
  the line, IF a single click produces a NESTED re-entrant pricing dispatch in one transaction (inner runs,
  outer effective pass skipped -> line keeps pre-dispatch/stale tier until next click).

WHAT WOULD HAVE TO BE TRUE (candidate's own CONFIRM signature)
  A debug log of ONE tiered 'Update Price' click showing AttributeVolume START count > 1 AND >=1
  'Skipping recursive execution'. i.e. the prehook re-enters execute() while a prior execute() is on the stack
  (between cls 72 set-true and cls 78 reset-false).

EVIDENCE GATHERED (all read-only)

1. CODE PATH — the write-back cannot re-dispatch the procedure (mechanism falsified).
   - submitContextUpdates (cls 610-634) calls industriesContext.updateContextAttributes(updateInput) — an
     IN-PLACE context-node write that returns synchronously. It does NOT run a Quote DML save and does NOT
     re-invoke the ExpressionSet. The ExpressionSet (pricing procedure) is the ORCHESTRATOR that CALLS the
     prehook; a prehook writing back to context is a leaf write, not a trigger for another procedure run.
   - place_action_log.txt trace: updateContextAttributes METHOD_ENTRY[7181]->METHOD_EXIT[7182] returns
     {isSuccess=true} immediately; no nested AttributeVolume START follows it. The prehook's own write-back
     (updateContextAttributes METHOD_ENTRY[10850]->EXIT[10851], 'Update result:{...}') likewise returns
     synchronously with NO nested re-dispatch.
   => There is no in-transaction re-entry vector. The only way the guard could trip is the platform itself
      re-invoking execute() re-entrantly — never observed.

2. SEVEN distinct pricing-transaction logs, all at APEX_CODE,FINEST (max verbosity, no debug suppression):
   place_action_log.txt, log-07LWC00000OqLKJ2A3, log-07LWC00000OqLQp2AN, log-07LWC00000OqQqF2AV,
   log-07LWC00000OqXWj2AN, log-place-04-34-13, log-aura-12-45-03
   EVERY log: AttributeVolume START=1, END=1, 'Skipping recursive execution'=0.
   Companion prehooks Hardware START=1, RegionalServices START=1 each — single dispatch each.
   place_action_log: class id 01pWC000001wAzJ appears as CODE_UNIT_STARTED exactly 1x;
   RevenueTransactionApexExecutor wrapper started 7x (one per Apex prehook/action) -> prehooks run in
   SEQUENCE as separate procedure steps, none re-triggers another. Zero nested re-entry of the prehook.

3. Statics reset per transaction; each 'Update Price' click is its own /connect/.../price-contexts
   transaction (ui-FINDINGS-summary.txt #3, ui-pricing-api-exec.json). So isUpdating starts FALSE every
   click and CANNOT carry stale state across the two clicks of the symptom. (Candidate concedes this.)

4. Single live class, single binding: Tooling API confirms one AttributeVolumePricingPrehook
   (01pWC000001wAzJYAU, ApiV64, LM 2026-06-10). No duplicate registration that could double-dispatch.

GAP / RESIDUAL (honest)
   None of the 7 captured logs exercises the TIERED path: all show 0 MATCH / 0 RESET / 0 'Attribute_Volume:'
   / 0 eligible items — they early-return at 'No eligible line items (Has_Attribute_Adjustment__c=true)'
   BEFORE any tier work or context write-back. So no captured log is a true tiered repro. A real tiered
   repro would require a live quote edit + click (DML / live mutation) = requires authorization, not done.
   HOWEVER, the refutation does not depend on a tiered log: re-entry would manifest as a SECOND
   AttributeVolume START / a 'Skipping recursive execution' regardless of tier outcome, because the guard
   check (cls 65) and the START debug (cls 61) both fire at the very top of execute() before any
   eligibility/tier logic. Their universal absence across 7 FINEST logs refutes the re-entry premise.

DRIFT NOTE (not load-bearing for this verdict)
   Live ACTIVE pricing procedure version is V12 (proc-version-status.txt), not V9 as stated in the task
   ground-truth. Dispatch mechanism (RevenueTransactionApexExecutor -> SignalingApexProcessor) is unchanged.

CONCLUSION
   The recursion guard is an INERT DEFENSIVE no-op on the observed paths. Its claimed click-twice mechanism
   (single click -> nested dispatch -> skipped effective pass) has no in-transaction re-entry vector in the
   code and is contradicted by 7/7 FINEST logs (always 1 START / 0 skip). REFUTED as the SC-3390 driver.
   The surviving, evidence-consistent hypothesis remains the one-cycle stale CONTEXT-SNAPSHOT lag
   (freshly typed Attribute_Volume not flushed into the FIRST click's context snapshot) — a separate
   mechanism, not this guard.
