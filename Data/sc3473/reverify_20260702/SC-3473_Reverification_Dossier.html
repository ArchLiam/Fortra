01

The failure, in one glance

Clicking Delete Group on a quote group throws a toast and leaves the quote unsaved. The exact wording is the whole tell:

Quote Line Editor · Delete Group · toast
Your quote was not updated.
Cannot invoke Object.toString() because the return value of
java.util.Map.get(Object) is null.

That string is not an Apex error. It is a JVM “helpful NullPointerException” (JEP-358), whose signature form is Cannot invoke X because the return value of Y is null. Apex null-dereferences read System.NullPointerException: Attempt to de-reference a null object and never name a java.util.Map. The throw comes from inside Salesforce’s managed Revenue Cloud pricing engine, not from any custom code — which is why it never appears in the reporter’s ApexLogs and cannot be fixed in Apex.

Mechanism What actually happens on Delete Group

The QLE Delete Group action calls the native Place Quote / Place Sales Transaction API with pricingPref = Force: it commits the quote header, cascade-deletes the grouped lines, then force-reprices the surviving lines. During that reprice, a TermDefined line carrying a null PricingTermCount presents a null term key; the engine does the equivalent of map.get(termKey).toString() → NPE. The header is not rolled back → “quote was not updated.” Live CalculationStatus = SaveFailedOrIncomplete on the original quote confirmed the engine’s save path fired and leaked the raw exception.

03

Why the defect kept coming back

This is the part that matters more than the single ticket. The null-PTC condition is not a one-off data glitch — it is regenerated by the pricing procedure itself whenever the writer that stamps PricingTermCount for TermDefined lines is missing.

Because PricingTermCount is read-only, only a pricing-engine step can set it. That step — a guarded TermDefined proration writer — has been dropped four separate times under the procedure’s element-ceiling pressure, each time silently re-opening the null-PTC gap that feeds the Delete-Group NPE:

Durable root cause An organizational one, not just a code one

The procedure sits at 128 of a ~129-element ceiling and is co-owned and churned. Every time someone reworks it near the limit, the multi-element TermDefined writer is the tempting thing to cut. The defect will keep returning until the requirement is written into the branch/PR checklist (§05, Phase 2).

04

The fix that is live — and why it costs zero elements

The clever part of this fix is that it needed no new procedure elements, so it slid in under the ceiling. The proration cluster already stamps PricingTermCount = 1 for the analogous Evergreen “no live end-date” case via a plain constant-assignment. The fix simply widens that one filter to also admit the broken TermDefined cohort.

The single edit — filter ListOperation93 (seq 29, container ListContainer92)

Before · TermDefined excluded → PTC stays null
# criteria
1  SellingModelType   Equals   'Evergreen'
2  AllowPartialProrationPeriods  Equals false
3  itemTransientEndDate          Is Null

# condition logic
1 AND (2 OR 3)
After · live in V21 — TermDefined admitted
# criteria
1  SellingModelType   Equals   'Evergreen'
2  AllowPartialProrationPeriods  Equals false
3  itemTransientEndDate          Is Null
4  SellingModelType   Equals   'TermDefined'

# condition logic
(1 AND (2 OR 3)) OR (4 AND 3)

The existing AssignmentElement in that container then stamps PricingTermCount = 1 on exactly the TermDefined lines that seq 27 filters out (those with a null transient end-date). It mirrors seq 27’s own (4 AND 3) TermDefined branch, so it is structurally consistent, and it touches neither Evergreen lines nor TermDefined lines that already prorate. Net element count stays 128 — under the ceiling.

Precision caveat Constant PTC = 1 fits all current data

Every healed TermDefined line observed = single full-term, PTC = 1. If Fortra ever needs a computed PTC for multi-term or partial TermDefined lines, that requires the 3-element proration writer (V20_writer_subtree_template.xml) plus reclaimed element budget — out of scope for stopping the NPE, and unsupported by any current data.

Rejected — don’t retry Approaches proven not to work

Naked Reprice-All as a “clear the wedge” lever — before the fix it force-repriced the same malformed line and re-threw. Merged single-BKM proration — one EffectiveTo can’t serve both Evergreen (transient) and TermDefined (real EndDate). Hydrating itemTransientEndDate in-proc — no procedure step writes that transient. Reclaiming the “Copy of List Container 8” / dual “Aggregate Price” steps — all confirmed functional (Services/Software/Subscription totals; two distinct group aggregations).

Honest limits carried forward from the RCA

  • Necessary, not proven-sufficient. Null PTC is a necessary contributing trigger, but ~83% of same-condition quotes org-wide priced fine — so it is a strong trigger, not a proven sole cause. This is exactly why the platform case (Phase 2) is the real guarantee against the raw NPE.
