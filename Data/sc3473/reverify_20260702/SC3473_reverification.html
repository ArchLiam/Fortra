§2 · What was originally concluded

The investigation under review

Symptom. Clicking Delete Group in the RLM Quote Line Editor throws a red toast:

Your quote was not updated. Cannot invoke "Object.toString()" because the return value of "java.util.Map.get(Object)" is null

Conclusion on file. The throw is a native, JVM-level "helpful NullPointerException" (JEP-358) inside the managed Revenue Cloud save/force-reprice engine — not custom Apex. The most-probable in-org data trigger is a malformed TermDefined quote line carrying EndDate = null and PricingTermCount = null, a state produced when the guarded TermDefined proration writer was dropped from the pricing procedure (the SC-3420 family). The prescribed remedy had two prongs: (A) restore PricingTermCount stamping for TermDefined lines, and (B) a Salesforce platform case for the engine leaking a raw NPE instead of an actionable message.

The RCA's own honest limit. Null PricingTermCount is necessary-here but not proven sufficient org-wide — ~83% (128/154) of quotes carrying the same malformed-term condition price cleanly. So Prong A removes the trigger; only Prong B guarantees against the raw NPE itself. This re-verification preserves that distinction rather than papering over it.

§4 · Root cause & the fix, mechanically

Why the line was malformed — and how the fix stamps it

PricingTermCount is a platform-managed, read-only field: only the pricing engine can write it, so the remedy has to live in the procedure. The proration cluster has two complementary branches. TermDefined lines were falling through the gap between them.

Seq 27 · before

Real proration writer — skips TermDefined

The Proration BKM that computes and outputs PricingTermCount only admits a line when its itemTransientEndDate transient is set. That transient is written by no step and is null for TermDefined lines during reprice — so they never enter, and PTC stays null.

# ListOperation85 (Evergreen anytime proration) (1 AND 2 AND 3) OR (4 AND 3) 1 SellingModelType = 'Evergreen' 2 AllowPartialProrationPeriods = true 3 itemTransientEndDate IsNotNull ← null for TermDefined 4 SellingModelType = 'TermDefined'
Seq 29 · the fix

Constant-assignment container — now catches it

This container already stamps a constant PricingTermCount = 1 for the analogous Evergreen "no live end-date" case. Adding one criterion routes the exact orphaned TermDefined cohort (transient null) into that same assignment. No new elements.

# ListOperation93 (constant PTC assignment) (1 AND (2 OR 3)) OR (4 AND 3) 1 SellingModelType = 'Evergreen' 2 AllowPartialProrationPeriods = false 3 itemTransientEndDate IsNull ← true for TermDefined 4 SellingModelType = 'TermDefined' ← ADDED ⇒ Assignment94: PricingTermCount = 1
Why the two branches never collide. Seq-27 requires itemTransientEndDate IsNotNull; seq-29's new branch requires itemTransientEndDate IsNull. They are mutually exclusive, so a TermDefined line that does prorate in seq-27 is never re-stamped by seq-29. The Evergreen branch is untouched. Constant values confirmed live: EvergreenPricingTermCountConstant = 1, OneTimePricingTermCountConstant = 0.
A precision on the causal label. Adversarial review (§6) correctly notes that PricingTermCount is an engine output, not the value the engine dereferences — so "null PTC is the root trigger" is slightly imprecise. The proximate null is the line's malformed-term state (null EndDate → null itemTransientEndDate → null proration multiplier), of which null PTC is a co-symptom. All are outputs of the same dropped SC-3420 writer, so they are perfectly confounded and the fix targets the correct defect family. Empirically, healing the line stamps both EndDate and PTC and flips the quote to CompletedWithPricing.
Measured precision limit — the constant is data-gated. A constant PTC=1 is correct only for single, full-term lines. A live count found 47 TermDefined lines with an engine-computed fractional PTC (0.57, 0.74, 0.83 … partial periods) and one at PTC=3 (multi-term) — all priced under earlier versions that still had a real proration writer. Under V21 there is no TermDefined proration writer, so re-pricing one of those lines could route it through the seq-29 constant and overwrite the correct multiplier with 1 (silent amount error). All 47 are currently quiescent (pre-fix), so the risk is latent, not active — but it must be tested before closure (Roadmap Phase 3). The durable answer for computed proration is the 3-element writer preserved in V20_writer_subtree_template.xml (needs element budget).

§6 · Adversarial review

Four attempts to break the conclusion

Each core conclusion was handed to an independent skeptic instructed to refute it. This is where residual risk gets named honestly.

Efficacy

"The fix won't actually stop the Delete-Group NPE"

Concern did not survive

The skeptic could not refute the fix's efficacy — the affirmative evidence (repro quote healed, malformed line now PTC=1, zero post-fix null-PTC lines) outweighs the counter-case. But the claim is "not proven to 100%," not "confirmed."

Named residual: the quote healed via a reprice, not via the delete-cascade + forced full-graph reprice path that actually throws. No successful Delete-Group has been observed post-fix. And the necessary-not-sufficient co-factor (~83% of same-condition quotes price fine) is unresolved. → Roadmap Phase 5 (logged repro) is the proof.
Safety

"The constant PTC=1 cannot cause a pricing regression"

Concern holds — confirmed

The skeptic refuted the safety claim by reading the live V21 body: there is no functioning TermDefined proration writer in V21, so the seq-29 constant is the only thing setting PTC for the entire TermDefined cohort. A flat 1 silently mis-prices any multi-year / non-annual / partial-period line.

Measured, not asserted: a live count found 47 TermDefined lines with a fractional PTC (partial-period) and one at PTC=3 (multi-term). All are pre-fix and quiescent, so the risk is latent — but re-pricing any of them under V21 could overwrite the correct multiplier with 1. Highest exposure: renewal / maintenance / COLA multi-year deals. → Roadmap Phase 3 settles it with one logged reprice.
Root cause

"PricingTermCount=null is the root data trigger"

Label imprecise — fix still right

The skeptic refuted the literal label: PTC is an engine output, so it cannot be the null the engine dereferences before producing it. The proximate null is EndDate → itemTransientEndDate. But EndDate-null and PTC-null are perfectly confounded (both outputs of the same dropped SC-3420 writer), so the fix targets the correct defect family and the healing outcome is genuine.

Consequence: because the exact native key was never captured and the co-factor is unidentified, the Salesforce platform case (Phase 4) is still required — it is the only guarantee against the raw NPE regardless of the data fix.
Durability

"The fix is durable"

Concern holds — high confidence

The skeptic refuted durability (while confirming the fix is correct and live right now). It is a single <criteria> node buried inside a filter step — not a discrete, self-describing element — in a co-owned procedure that sits at 128 of ~129 elements (verified: 32 filters + 64 BKMs + 32 groups). This exact branch has now been dropped 3× (V12, V17-19, V21).

Minimum durable guard: mirror into V22 now, and add "TermDefined must receive a non-null PricingTermCount" to the pricing-procedure PR/branch checklist with an element-budget note. → Roadmap Phase 2.
