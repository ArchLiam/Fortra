## 4. Root cause

Three **distinct** defects, all triggered by one underlying pricing shape: these products are
**attribute/derived-priced** — the net price ($875, $4,356) is computed from product attributes and
sits **far above** the list-price base (`TotalLineAmount` = $0, $46). So `TotalAdjustmentAmount` is a
large **positive markup**, not a discount. Every field that assumes "net ≤ list" then inverts.

### RC1 — Phantom discount + wrong ALE  *(the "very large discount" and "ALE incorrect")*
- `Subtotal` rolls up **list** (`TotalLineAmount` = $46); `TotalPrice` rolls up **net** ($5,231).
- Standard `Discount = (1 − TotalPrice/Subtotal) = −11,271.7 %` — Salesforce reports the net-over-list
  gap as a (massive, negative) discount.
- `ALE__c` and `Annualized_License_Equivalent_Base__c` are **formula = `Subtotal`**, so they inherit the
  $46 list base instead of the real annualized subscription value (~$5,231).

### RC2 — Negative `Total_Discount_Amount__c`  *(part of the "large discount displayed")*
- Live formula: `Total_Discount_Amount__c = (−1) × SUM(TotalAdjustmentAmount)`.
- The formula assumes adjustments are **discounts** (negative). Here they're **markups** (positive
  $5,185), so `×(−1)` yields **−$5,185**. A markup is being surfaced as a negative discount.

### RC3 — Phantom `Total_Services__c = $500`  *(the "Services Total with no Services")*
- Both lines are `Fortra_Product_Type__c='Subscription'`, so the **Services group is empty**.
- `Total_Services__c` is a **stored** field written by a *conditional* aggregate. When the group is
  empty the aggregate **does not write 0 — it leaves the prior value**, so a **stale $500** from an
  earlier pricing pass (when a Services line existed/was mis-typed) survives.
- Proof it's stale, not a default: `Total_Software__c = null` (never written → no Software line ever),
  while `Total_Services__c = $500` (written once, never reset). There is **no literal `500`** anywhere
  in the procedure (grep-confirmed across all versions).

## 5. Proposed solution

> All changes are **pricing-procedure config + a formula field** — no Apex. Make them on a **fresh
> retrieve of the live UAT ExpressionSetDefinition**, then deploy back. **No changes made yet — UAT
> deploy needs explicit go-ahead.**

### Fix RC3 (stale Services total) — lowest risk, do first
Initialize the category/discount totals to **0 at the start of every pricing run**, before the
conditional aggregates, so an empty group resolves to `0` instead of leaving stale data. Two ways:
- **(Preferred)** Add an Assignment step at the top of the procedure that sets `Total_Services__c`,
  `Total_Software__c`, `Total_Subscription__c`, `Total_Discount_Amount__c` = 0.
- Or make each aggregate **unconditional** and gate the value with an inline `IF(type=…, net, 0)` so
  every run writes a number (including 0).

Backfill existing stale records once (set `Total_Services__c = 0` where no Services line exists), or
just re-save/reprice affected quotes after the fix.

### Fix RC1 (Subtotal / Discount / ALE) — **needs a business decision** (see §6)
The right fix depends on what these products' "list price" is *supposed* to be:

- **Option A — list price should equal the attribute price (data fix).** If `ListPrice` simply isn't
  maintained (beSECURE = $0, Abstract = $46) and the real price is the attribute price, fix the
  **PricebookEntry / list-price setup** so `TotalLineAmount` aligns with net. Then `Subtotal == TotalPrice`,
  `Discount → 0`, and ALE is correct automatically. *Cleanest if attribute pricing is meant to be the list.*
- **Option B — derived/attribute pricing is intentional (config fix).** If list is deliberately a
  placeholder, stop tying customer-facing fields to it:
  - Re-point `ALE__c` / `Annualized_License_Equivalent_Base__c` formula from `Subtotal` to the **net
    annualized** value (e.g. `Total_Subscription__c`, or `TotalPrice` normalized by term).
  - Change the header `Subtotal` aggregate to roll up **net** (`NetTotalPrice`) so the standard
    `Discount` stops inverting, **or** hide the standard Discount field on the layout and rely on
    `Total_Discount_Amount__c` (after RC2 is fixed).

### Fix RC2 (negative discount amount)
Only count **actual discounts** (negative adjustments): clamp positive adjustments out, e.g.
`Total_Discount_Amount__c = (−1) × SUM(MIN(TotalAdjustmentAmount, 0))`, or sum only lines where the
adjustment is < 0. Markups then read as `$0` discount rather than a negative number. (If markups must
be shown, surface them in a separate "Total Adjustment / Uplift" field, not the discount field.)

### 10.3 The `ListPriceBuffer__c` finding (don't chase a ghost)

`ListPriceBuffer__c` is **referenced once** (read-only, in the `DiscountPercent` formula) and is **never
written by any step, never declared as a variable, and is not a field on Quote or QuoteLineItem**
(verified via SOQL + grep). It is a **dangling reference**. On the XML alone the formula should hit its
`ELSE` branch and yield `0`. The displayed −11,271.739% is fully explained by the **standard
Salesforce-derived Discount** `(1 − TotalPrice/Subtotal)`. **Implication:** fixing `Subtotal` (10.4 step 1)
cures the discount % regardless; just delete/repair the dangling `ListPriceBuffer__c` reference for hygiene.

### 10.4 Fix plan — author a new version (do not patch V6 in place)
