# SC-3339 — Carry Bill To / Ship To (Account + Address) from Quote to Order (and Opportunity) on conversion

> Space: Salesforce-Coastal · Type: Feature ("Improve Feature")

> 📋 **Deep investigation complete (2026-06-05)** → see [INVESTIGATION.md](INVESTIGATION.md).
> **Key result:** the Address half is *already mapped* (flow element `Update_Order_Record_with_Bill_to_Ship_To_Address`). The real gap is the **Account half** — `Order.Bill_To_Account__c` / `Ship_To_Account__c` are never populated, which **blocks Workday submission** (`Order_Submit_Validation__mdt` X00024/X00025 are Active and require them). Resolved source: the **Place's parent Account** (`Quote.Bill_To_Place__r.Account__c` / `Ship_To_Place__r.Account__c`) — 99.3% confirmed against live UAT data. Implement as a new **header method on `QuoteToOrderFieldMapper`** (the existing mapper is line-level only).

## Finalized Decisions (2026-06-05, from stakeholder)

| # | Question | Decision |
|---|---|---|
| Q1 | Account source / override | **Derive from the Place's parent Account** (`Place.Account__c`); set **only when the Order field is null** (never overwrite an existing value). |
| Q2 | No Bill/Ship To Place on Quote | **Leave the Order Account null** — no fallback. (It then fails X00024/X00025 → manual completion, which is the correct signal.) |
| Q3 | Bill vs Ship independence | **Treat independently** — derive each Account from its own Place. |
| Q4 | Place lookups + Place-vs-Address | **Data-driven (resolved):** the Order **Place lookups are already populated** by `createOrderFromQuote`/Context Mapping (21,353 / 15,390 Orders; 0 converted Orders missing them) → **do NOT add Place mapping.** Place and Address are the **same Places record** (~98%). The only gap is the **Account** fields (only 157/153 of 28,949 Orders have them). |
| Q5 | Opportunity | **Out of scope** — no Opportunity changes. |
| Q6 | Downstream use of Account | **Don't touch** — assume submission-check (X00024/X00025) only. |

**Resulting build (minimal):** add a header method to `QuoteToOrderFieldMapper` that sets, when null:
`Order.Bill_To_Account__c = Order.Bill_To_Place__r.Account__c` and `Order.Ship_To_Account__c = Order.Ship_To_Place__r.Account__c` (the Order's own Place is already populated by the time it runs). Wire it into `Fortra_Quote_to_Order_Conversion` after the address update / before contract+reprice. No Place mapping, no Address mapping, no Opportunity, no flow Place changes. + test class to ≥75%.

## Background

Bill To / Ship To values aren't carrying from the Quote to the Order/Opportunity. Cassie asked: *"Shouldn't the bill-to account and ship-to account populate based on the data from the quote and/or opportunity?"* Jomil believed a ticket already existed to make these values carry over.

The Quote→Order conversion is **Apex-driven**. The standard `createOrderFromQuote` action does **not** map custom lookup fields; the new `QuoteToOrderFieldMapper` invocable bridges that gap (currently maps `Hardware__c`, `Hardware_ID__c`, `Partition_Reference__c` → `Partition_Record__c`, and `Ship_To_Address__c` from `Quote.Ship_To_Place__c`). **Bill To Account and Ship To Account are not currently mapped** onto the Order.

> 🔎 **Investigation correction:** The *Address* half (`Bill_To_Address__c` / `Ship_To_Address__c`) **is** already mapped at the Order header by flow element `Update_Order_Record_with_Bill_to_Ship_To_Address`, plus the line-level `OrderItem.Ship_To_Address__c` by the mapper. The genuinely-missing piece is the **Account** half (`Bill_To_Account__c` / `Ship_To_Account__c`) and the Order **Place lookups** (`Bill_To_Place__c` / `Ship_To_Place__c`, currently unset). See [INVESTIGATION.md](INVESTIGATION.md) §1.

---

## Scope / Approach

Extend the existing conversion automation so Bill / Ship To carry over:

- Add a **header-level method to `QuoteToOrderFieldMapper.cls`** (existing mapper is OrderItem/line-level only) to set, on the Order header, **only when null**:
  - `Bill_To_Account__c` = `Order.Bill_To_Place__r.Account__c`
  - `Ship_To_Account__c` = `Order.Ship_To_Place__r.Account__c`
  - **Do not** map Place lookups (already populated by createOrderFromQuote/Context Mapping) or `*_Address__c` (the flow already owns those). Accounts are the only gap.
- Wire the new invocable into `Fortra_Quote_to_Order_Conversion` **after** `Get_Created_Order` / the address update and **before** `Decision_Create_Contract_Record` (so it runs after power-split and before SC-3308 reprice/activation + Workday validation). **Retrieve the current UAT flow as the edit base** (SC-3308 is deployed but not in local source).
- **Opportunity: out of scope** (Q5).
- Source fields confirmed against **live FortraUAT schema** (Order object isn't in local source — drift). Describes saved to [Data/sc3339/schema/](../../../Data/sc3339/schema/).
- Add test coverage — the existing mapper has **0% coverage** (no local test). Target ≥75% with header + line assertions.

## Open Questions (for stakeholders)

1. **Override rule:** ~0.7% of live Orders have Bill To Account ≠ Place's parent Account (manual/partner billing). Confirm "derive from `Place.Account__c`, never overwrite a pre-set value" — or should `Billing_Partner__c`/`PartnerAccountId` win for Bill To?
2. **Null-Place fallback:** When `Quote.Bill_To_Place__c`/`Ship_To_Place__c` is null, leave the Account null (fails X00024/X00025, manual completion) or fall back to `Quote.AccountId`/another default?
3. **Independence:** Can Bill To and Ship To Account differ on one Order, or always the same?
4. **Opportunity:** In scope? If yes, limited to the two Place fields; confirm direction/timing.
5. **Place vs Address pair:** Populate the Order `*_Place__c` lookups (only `*_Address__c` set today), or are Place and Address meant to be the same Place?
6. **Downstream:** Are the Account fields consumed beyond X00024/X00025 in a way that constrains acceptable values?
