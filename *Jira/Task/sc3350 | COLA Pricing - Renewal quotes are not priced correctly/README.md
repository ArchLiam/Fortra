## 0. The one‑paragraph truth

The two stated defects **both still reproduce in live right now**. COLA renewal pricing is implemented
**twice** (a `COLAUpliftHandler` trigger + a `COLAUpliftPrehook` pricing prehook), and renewals are
generated by a flow that **does not force a pricing pass**, so on a headless renewal only the trigger runs —
and the trigger bails before it can stamp COLA. Marc's rework **today** was a **pure testability/coverage
refactor**: it lifted the brief's coverage NO‑GO (Handler 42%→**91.8%**, Prehook 3%→**75.1%**, ACQH
0%→**86%**, QLDescGen→**80%** — all now clear the 75% gate) **but changed zero pricing behavior**. So the
remaining peer‑review blockers are now **functional + packaging**, not coverage. The biggest correction to
the prior brief: **"RLM renewals can never reprice" is false** — the platform's `initiateRenewal` has a
`skipPricing` toggle and `Asset.PricingSource` decides list‑vs‑last‑price; Fortra's renewal flow simply
omits both. That reframes the fix from "work around a platform limitation" to "use the supported levers."

## 3. Defect #1 — Renewal priced at list (COLA never applied)

**Root cause is in the trigger/headless‑renewal path and is UNCHANGED by today's edits.** Two distinct
failure modes:

1. **QuoteActionId before‑insert race (primary).** `COLAUpliftHandler.handleBeforeInsert` collects
   `QuoteActionId` only off the inserting rows and **early‑returns when empty** (live
   [evidence/live-classes/COLAUpliftHandler.cls](evidence/live-classes/COLAUpliftHandler.cls) L23‑31). The
   RLM renewal engine sets `QuoteActionId` **~34s after** the QLI insert, so the trigger short‑circuits and
   the line keeps list price. `handleBeforeUpdate` can't self‑heal — its recalc is gated on
   `Pre_COLA_Price__c != null` (L161), which is null on a never‑stamped line.
   - Live proof: repro `0QLWC000003bHpl4AE` (Quote `0Q0WC00000365Uj0AI`, Brand Protection, asset
     `02iWC000007DXlJYAW` price 10000, active 5% rule → expected **10500**) is still `UnitPrice=10000`, all
     COLA fields null, `LastModifiedDate == CreatedDate` (never re‑touched). QuoteAction
     `7ocWC00000tYaFtYAK` `LastModifiedDate` is 34s after the QLI insert.
2. **Null SourceAsset.Price bail (secondary, newly isolated).** Handler `continue`s when the source asset
   price is null (L291). e.g. `0QLWC0000031Lgb4AE` (Email Security, Unit=List=560.88, COLA null). 3 of 43
   renewal lines have a null source price.

**Population (corrected — the brief's "0 of 1,222,003" was a whole‑table miscount):** the true renewal
universe is **43 QLIs** (own `QuoteAction.Type='Renew'`) / 52 under 32 renewal quotes. Of 43: 40 are
COLA‑stamped, and only **2 are clean defect‑#1 at‑list repros (~4.7%)**. The stamp split is **13 in‑insert /
28 on‑update** (was 13/21; +7 lines created since the brief) — the fingerprint of an unreliable before‑insert
path rescued most‑of‑the‑time by the later write‑back.

**Subtle but important** (from the ticket testing records): on the audit renewal `0Q0WC000003671t0AA` the
trigger *does* base COLA on the right number (`Asset.Price` 4356/875, not list), so `UnitPrice` is correct
(4697.946 / 929.25). What's wrong is that **the Net/Subtotal/Total rollups don't pick up the COLA'd
UnitPrice** — both renewal quotes show `GrandTotal=0`, `NetUnitPrice=NetTotalPrice=TotalPrice=0`. That
zero‑rollup is the live fingerprint that **no full pricing‑procedure reprice ran on the renewal**. The two
test quotes even diverge from identical inputs (audit‑fields‑ok/rollup‑bad vs rollup‑ok/audit‑fields‑null) —
evidence of the timing race, not a deterministic single mode.

[evidence/research-notes/live_ticket_records.md](evidence/research-notes/live_ticket_records.md).

## 4. Defect #2 — Renewal lines get no Line Item Description

**Root cause UNCHANGED:** `QLDescriptionGeneratorPrehook` (a `SignalingApexProcessor`, "register LAST")
only runs **during a pricing‑procedure reprice**. Renewals never reprice → it never fires. The prehook's
code, attribute hydration, and writeback are all **correct** — proven by **162** non‑renewal lines getting
generated descriptions (11 of them today, after Marc's 14:41Z edit), while **0** renewal lines have one.

**Live proof:** a renewal line (`0QLWC000002UYeI4AW`, `Description=null`) and a non‑renewal line
(`0QLWC000003cIGm4AM`, `Description='beSECURE - Premise-Based | Devices: 1-10 | On Demand | Premise Based'`)
both carry a complete 4‑attribute set — so the renewal is **not** missing inputs; the only difference is
`QuoteAction.Type='Renew'`. **No renewal line was modified at all today**, so Marc's 14:41Z edit had zero
observable effect on renewals.

**Wrinkles to honor in the fix:**
- `submitContextUpdates` **silently swallows** "not in updatable state" and returns SUCCESS
  ([evidence/live-classes/QLDescriptionGeneratorPrehook.cls](evidence/live-classes/QLDescriptionGeneratorPrehook.cls) ~L695). If the renewal reprice runs in a non‑updatable context, description writes drop invisibly.
- The `DescriptionLinePrehook` chain order is **UI‑only RLM config** (not in retrievable metadata). If COLA
  adds its own prehook it must run **before** the description prehook. Capture as a change‑controlled runbook step.
- This is the **same class** as SC‑3349 but a **different failure mode** (never‑fires vs wrong‑content) — confirm whether #2 folds into SC‑3349's shipped fix or is tracked here.
Detail: [evidence/research-notes/live_defect2_descriptions.md](evidence/research-notes/live_defect2_descriptions.md),

## 6. Platform mechanism — the corrected central thesis (NEW)

The prior brief framed "renewals never run a full reprice" as an inherent RLM property. **Web research
against the Salesforce Revenue Cloud Dev Guide (v67, Summer '26) corrects this:**

- `initiateRenewal` has an explicit **`skipPricing`** boolean (v64+): perform vs skip the pricing procedure.
  Repricing on renewal is a **first‑class, parameterized option** — not impossible.
- **`Asset.PricingSource`** (`LastTransaction` vs `PriceBookListPrice`) is the **decisive native control for
  defect #1**: a fixed‑% uplift is *ignored* unless the base is `LastTransaction`. "Priced at plain list" is
  the documented symptom of `PriceBookListPrice`.
- Fortra's active renewal flow **`Fortra_Create_Renewal_Quote` v6** (Marc DeBrey) calls `initiateRenewal`
  but **omits `skipPricing`** and does **no** post‑call reprice — pricing is left to platform default +
  `Asset.PricingSource` + procedure config, none forced.
- There is a **second** active renewal flow, **`Fortra_Renewal_Quote_Creation` v1** (Joe Martinez), that
  bypasses `initiateRenewal` entirely and manually inserts QLIs relying on the trigger. **Which flow the live
  Renew button uses is unresolved** and determines whether the pricing engine is even in the picture.
- Forcing a reprice is supported via **Place Sales Transaction** with `pricingPref=Force` (Place **Quote** is
  deprecated as of v63 — don't use it). A forced reprice runs the whole prehook chain → fixes **#1 and #2
  together**.
- Salesforce's recommended uplift architecture is the **pricing layer** (native `PriceRevisionPolicy` +
  `IndexRate` + `PriceRevision`, or a `SignalingApexProcessor` prehook gated on `OriginalActionType=Renew`) —
  **never a trigger**. Fortra's all‑custom Apex COLA stack may be reinventing native capability.
- Documented native $0 footgun: **Get Renewable Assets Summary does not support Procedure Plans** → renewal
  lines can return $0 independent of custom code.

Full citations + URLs: [evidence/research-notes/context_platform_web.md](evidence/research-notes/context_platform_web.md)
and the dedicated [02_PLATFORM_MECHANISM.md](02_PLATFORM_MECHANISM.md).

## 7. Scope fork — single‑year vs the spreadsheet's multi‑year model

> **RESOLVED 2026‑06‑10 by the canonical User Story** ([evidence/USER_STORY.md](evidence/USER_STORY.md)): the
> spec is **single‑year only** (Req #5 = `Base × (1 + COLA%/100)`, no out‑year/MyCAP/compounding). **Option A
> is canonical.** The live out‑year/MyCAP machinery is **out‑of‑spec gold‑plating** — remove or shelve it;
> do not ship the broken `Final_Year` formula. The conformance audit is
> [03_USERSTORY_CONFORMANCE.md](03_USERSTORY_CONFORMANCE.md). The remainder of this section is retained for
> context on why the fork existed.

This decides the *size* of the ticket.

- **All three design docs** (COLA SDD v2.0, Confluence Overview, Increase Table) mandate **single‑year only**:
  `UnitPrice = Asset.Price × (1 + COLA%/100)`, renewal‑only, 3‑tier override. No out‑year / MyCAP /
  compounding anywhere. The live **year‑1 path implements this faithfully** (verified to the penny).
- **Leah Guenther's ticket spreadsheet** is richer: **multi‑year compounding** (Base+Cola 200→206→212.18;
  Renewal Maintenance Total 140→144.20→148.53, ×1.03/yr) on **both** license and maintenance, with the
  **year‑1 rate** (CMDT 4.7–12%) **distinct** from the **out‑year rate** (MyCAP 3%).
- **Live truth (tie‑breaker):** the out‑year **rate** *is* alive — today's `COLAUpliftHandler` defaults
  `COLA_Outyear_Uplift_Percent__c` from `MyCAP_Rules__mdt`=3 on multi‑year lines — but the compounded
  **price** field `Final_Year_COLA_Calculated_Price__c` is referenced **0×** in the active V10 procedure and
  **0×** in live Apex. **The system computes the multi‑year number and bills the single‑year one.** And the
  formula is broken (compounds the wrong base; uses `PricingTermCount` (months) as a years exponent with no
  unit guard). Live note: the field currently throws `INVALID_FIELD` on SOQL — possibly in a compile‑error state.

→ **Decision for Marc/German:** is SC‑3350 **Option A** ("fix the two documented year‑1 defects + the
description") or **Option B** ("finish wiring the spreadsheet's multi‑year compounding for license +
maintenance" — large blast radius, requires fixing `Final_Year` first)?
Detail: [evidence/research-notes/context_scope_fork.md](evidence/research-notes/context_scope_fork.md).
Even under Option A, year‑1 is incomplete: **per‑product rate exceptions** (Systems Management `Messenger*`
12% vs 7.85%; Cybersecurity SecureCare/SSO 4.70% vs 7.85%) can't be expressed by a CMDT keyed only on
`Solution_Category__c`.
