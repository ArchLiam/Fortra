Root cause 1

No shared, version-controlled source of truth

The problem

  • The live org — not git — is the operative source of truth. Changes are authored directly in the org and retrieved after the fact.
  • The repository that exists is a single-author working copy with no pull-request history, no shared promotion path, and (verified) no CI configuration.
  • So collaboration happens by editing the live org directly — no diff, no review, no rollback.
  • This is a process gap, not a people problem: without a repo + pipeline + review, even careful engineers clobber each other's work.
Evidence (checkable)
No shared team repo and no .github/workflows CI in the codebase — confirmed today.
Production gack from an in-place edit to the live pricing procedure — context wasn't re-synced (reprice contextDefinitionName).
A flow change silently re-introduced a closed defect; caught late and fixed only by reverting (SC-3368 line-type).
A pricing formula that oscillates between sessions because its state lives only in the live org (derived-tier V-series).
ImpactEvery fix starts from "what is actually live right now" — the re-discovery tax that drives the dev ↔ test loops, and the reason work is hard to hand off safely.

Root cause 2

Quality gates aren't continuous

The problem

  • Test coverage is treated as an end-of-build task, not a per-ticket habit.
  • Org-wide Apex coverage is well below the level Salesforce requires to deploy to production.
  • Several in-scope pricing classes sit at very low coverage (2–37%).
  • This is a hard platform gate — not a preference: the production deploy is rejected until it clears, regardless of business sign-off.
Evidence (checkable)
Org-wide Apex coverage ~43–45% vs the mandatory 75% production gate.
In-scope pricing classes measured at 2–37% (authoritative peer-review run).
A same-day remediation pass moved overall coverage only 43% → 45%.
No CI config in the repo to catch this continuously.
ImpactA hidden cutover blocker: go-live is gated until coverage clears 75%. Far better surfaced now than at the deadline.

Root cause 3

Overlapping automation & an overgrown pricing engine

The problem

  • Multiple automations do overlapping work on the same transaction; the pricing engine keeps growing in place.
  • On large orders this overflows Salesforce governor limits (SOQL & Apex CPU).
  • "Optimize existing flows and Apex" — raised by the team — sits precisely here.
  • Accreted, duplicate automation consumes the shared governor budget and makes every change riskier.
Evidence (checkable)
3 OrderItem flows fan out per line → 51 flow interviews on a 17-line order → "Too many SOQL queries: 101" (UAT).
A redundant duplicate subflow was the single largest contributor (~40%) — doing work an active flow already did.
A high-quantity convert breached the Apex CPU limit (401 line clones, 1,293 flow interviews).
Pricing procedure: ~128 steps across 22 in-place versions, 9 pre/post-hook classes (2 redundant pairs). Org-wide, 46 of 180 record-triggered flows are inactive but still shipped (next slide).
ImpactLarge / high-value orders fail in UAT until the automation is consolidated and SOQL is lifted out of loops.

Root cause 4

Scope & solution design not pinned down in discovery

The problem

  • Volume, pricing math, validations and migration feasibility were discovered during build/UAT, not up front.
  • The end-to-end solution design isn't fully articulated — e.g. lookup filters and field-level validations (team-raised).
  • No non-functional / volume requirements were captured; the realistic order-line ceiling is still an open question to the PO.
  • Core pricing rules remain open (multi-currency, margin-vs-discount, new vs renewal maintenance).
Evidence (checkable)
Design docs contain essentially no volume / NFR requirements; order size assumed far below business volumes.
Two governor defects found reactively in UAT (SOQL on large orders; CPU on high-qty converts).
~24 distinct pricing / Workday tickets worked in a ~3-week window.
Migration: ProductConfigurationRule + ≥8 other RCA objects had no supported migration path — found one-by-one during cutover.
ImpactThe long tail of reactively-discovered gaps is the budget story — each gap becomes its own RCA → fix → retest loop.

Connecting the dots

How these root causes produce the loops & the overrun

Scope gap

A requirement (volume, pricing rule, validation) wasn't pinned down.

›

Surfaces in UAT

It fails during testing as a defect — not a known, planned task.

›

Edit live to fix

With no repo / review, the fix is made directly in the org.

›

Clobber / regress

Another in-place edit re-breaks it, or a closed defect returns.

›

Re-investigate

Next engineer re-retrieves to learn "what's actually live."

↺…and back to UAT — the same loop repeats, multiplied across ~24 tickets and every large order.

Note: that this is the primary driver of the overrun is a reasonable inference from the pattern, not a measured share. The pattern itself — gap → UAT defect → live edit → regression → re-investigation — is well evidenced.

The mechanism, up close

The delivery loop, dissected — where each lap leaks time

Our cycle is develop → peer review → user testing → back to develop. On paper that's healthy. In practice, none of the four hops is a checkpoint that stops a defect before UAT — so each lap re-pays the same tax.

1 · Develop

Fix authored directly in the live org.

No branch, no diff — the change has no record of what it touched.
›

2 · Peer review

Reviewer inspects the org's current state.

Reviews an org, not a diff — can't see what changed, so regressions pass.
›

3 · User testing

Defects first surface here, in UAT.

The most expensive place to find a bug — incl. ones a gate would catch earlier.
›

4 · Back to develop

Next engineer re-retrieves the org.

Re-learns "what's actually live" before touching anything — the re-discovery tax.
↺The loop has no early exit. A diff, a review of that diff, and an automated gate would each stop a defect one hop sooner — and one order of magnitude cheaper.

The honest read

Why delivery keeps slipping

It isn't slow engineering — it's rework

  • Defects are found late. With no diff-review and no CI, the first gate is UAT — the costliest place to catch anything.
  • "Fixed" can't be proven. No diff and no automated test gate means a fix is verified by hand, so the same ticket re-opens.
  • The same wall, every large order. Because volume was never pinned, governor limits re-surface instead of being designed out once.
  • Every lap costs re-discovery. Each change begins by re-establishing what is live — work that produces nothing shippable.
The shape of the cost
~24 pricing / Workday tickets worked in a ~3-week window — many are the same loop re-run.
Two governor defects and one production gack were found reactively, not designed out.
A closed defect came back because no review saw the change that re-broke it.
This is a structural throughput ceiling, not a matter of hours worked.
The pointThe team is moving fast inside a loop that keeps handing work back. Fix the loop, and the same effort ships.
